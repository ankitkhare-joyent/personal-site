Ingesting 10,000 PagerDuty incidents without fighting Spark

Ankit Khare · November 2026 · 3 min read

We wanted our full PagerDuty history in the lakehouse: incidents, their log entries and their alerts. The first version took one and a half to two hours a run. The faster version then broke on a Spark limit I had never needed to know about.

Version one: one request series per incident

Each run refetched about 10,000 incidents, then walked each incident's log entries and alerts. That is tens of thousands of paginated requests, and with five worker threads it took 1.5 to 2 hours.

Use the bulk endpoint, and check it every run

PagerDuty has an account-wide log entries endpoint, so the job now fetches log entries for the whole time window in six-hour slices and groups them by incident. A slice that hits the API's 10,000-result offset cap is split in half and fetched again. Entries are de-duplicated and kept in the API's order, newest first, because tables built later depend on that order.

Switching from a per-incident source to a bulk one is the kind of change that can drift without anyone noticing, so the job checks itself. Every run picks a sample of incidents (the busiest half plus an even spread, 20 by default) and fetches them the old way. If the entry IDs or their order differ for any of them, it logs a warning and falls back to the per-incident path for every incident. A config flag forces the old path too.

One rate limiter, set by measurement

Alerts have no account-wide endpoint, so they are still fetched per incident, alongside the bulk log entries. Ten driver threads share a single rate limiter. PagerDuty allows roughly 960 requests a minute per key, and I started at 840. Another scheduled job used the same key, and at 840 we drew 429 responses with about 25-second Retry-After waits every minute. At 600 a minute the run was just as fast, with none.

The 128 MB surprise

The first full run on staging fetched everything (10,258 incidents, 113,000 log entries and 10,000 alerts in about 18 minutes) and then failed. Our shared write helper sent each dataset's JSON through a single Spark task, and the incidents dataset came to 237 MB, over Spark's 128 MB spark.rpc.message.maxSize. The Spark operator restarted the job, which started the 18 minutes again.

The fix was to stop using Spark for that step. Ingestion now writes each dataset straight to S3 with PyArrow from the driver, in the same layout and file formats as before, and frees each dataset once it is written. A failed write raises instead of being logged and ignored. The flatten job that reads the files only picks up *.parquet, since the folder also holds the JSON copies.

Right-size the job to what it does

The API work is network-bound threads on the driver, and the only Spark work left is writing 13 files. So the DAG went from a 2-core driver plus two to five 2-core executors with dynamic allocation to one driver core and a single 1-core executor.

Tests with a fake API

The tests run against a fake PagerDuty API and check that bulk and per-incident modes produce identical datasets (including the derived tables and same-second ties), that a mismatch triggers the fallback, that late entries are ignored, that the offset-cap split works, and that the limiter spaces requests correctly.

Takeaways

  • Spark is a poor HTTP client. Use it where the data is big. When the work is many small requests, threads on one machine and a plain file writer are simpler and cheaper.
  • A faster source needs a built-in check. Comparing a sample against the slow path on every run lets you take the speed and still sleep.
  • Rate limits are shared. Measure 429s with everything else that uses the key running, not the documented limit.
  • Know your framework's size limits before your data finds them for you.

A Spark 3.5 optimizer crash that a cache was hiding

Ankit Khare · November 2026 · 3 min read

A production table started failing on every retry with an error that looked like it belonged to someone else: an internal assertion inside Spark's optimizer. The cause was a perfectly reasonable join key, and a cache had been hiding it.

The error

[INTERNAL_ERROR] The Spark SQL phase optimization failed with an internal error.
java.lang.AssertionError ... at PushablePredicate ... V2ScanRelationPushDown

It came from a job that builds a dimension table out of several reference views over Iceberg. Retries did not help, and nothing in our code was in the stack trace.

What was actually happening

The reference views were keyed on nullif(trim(id), ''), so blank IDs became NULL and joined to nothing. That is a common idiom and it was correct. The trouble was what Spark did with it:

  1. For an inner join, Spark infers key IS NOT NULL on both sides.
  2. It pushes that predicate down, through a max_by aggregate, toward the Iceberg scan.
  3. Spark 3.5.1 simplifies IsNotNull(nullif(...)) into a top-level If expression.
  4. The translation from Catalyst filters to data source V2 filters asserts that every predicate it is handed can be translated. That If cannot, so the optimizer crashes.

Why only now? An upstream persist() meant later plans reused the cached result instead of planning the pushdown again. When an unrelated change made the plans stop matching the cached ones, every run planned the pushdown, and every run failed.

The fix

Key the views on trim(id) instead. Blank keys now group under '' rather than NULL, and they still join to nothing, because every column they are compared with is itself nullif'd. I reproduced it with PySpark 3.5.1 and Iceberg 1.5.2 using the real views: the old code fails without the cache, and the new code passes with and without it, with the same output.

It came back ten days later

A different job hit the same assertion from filters on Iceberg reads:

-- before: not translatable to a V2 filter
NULLIF(TRIM(service_name), '') IS NOT NULL
NOT COALESCE(is_deleted, false)

-- after: same meaning, plain pushable predicates
service_name IS NOT NULL AND TRIM(service_name) <> ''
NOT (is_deleted <=> true)

This time the more interesting fix was the test. All of that job's tests ran on in-memory DataFrames, where nothing is pushed down to a data source, so they could never see this class of bug. I added a test that runs the job's SQL against real local Iceberg tables. It fails on the old code with the same AssertionError and passes on the new code.

Takeaways

  • Filters on a scan should be boring. Plain columns, comparisons, IS NULL, IN. Wrap the clever expressions around the result, not inside the predicate the optimizer will try to push down.
  • A cache can hide a planner bug. If something fails "suddenly" after an unrelated change, check whether a persist() used to short-circuit the plan.
  • Test against the real format. In-memory DataFrames skip pushdown, file pruning and the data source's own rules. One test on real Iceberg tables catches what a hundred in-memory ones cannot.
  • Reproduce before you guard. Wrapping the job in a retry or a try/except would have hidden this again. Pinning the exact versions and the real views turned an "internal error" into a one-line fix.

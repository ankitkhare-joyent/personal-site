ignoreCorruptFiles turned a network blip into a missing day

Ankit Khare · November 2026 · 3 min read

Backfills of our data-center inventory kept coming back with holes: a day of VMs here, three days of interconnects there. Every run reported success. Rerunning a single day loaded it in full. That combination is the signature of a silent skip.

Where the rows went

Our shared Parquet read helper set Spark's ignoreCorruptFiles option to true by default. The option exists so one damaged file does not fail a large read. What it actually does is broader: any exception while reading a file, including a transient S3 error, makes Spark skip that file and carry on.

A range backfill reads many files at once, so it is the most likely to hit a transient error. The file for that day was skipped, the day had no source rows, and the load did exactly what an Iceberg MERGE does with no rows: nothing. The table kept its old contents for that day, the job went green, and nobody knew.

The second cause, found on the way

One export changed format: a wider, 438-column version of the file wrote an integer column as INT64, where the job declares a 32-bit IntegerType. On the cluster Spark could not convert it, treated the file as unreadable, and skipped it. That day loaded 0 of 273,590 rows, again with a green run.

The fix

  • Turn the option off for this source. With ignoreCorruptFiles false, Spark retries the task, and a failure that persists fails the run with the file path in the error.
  • Read each file with its own integer widths. The job takes the column types from each file's Parquet footer, reads with those, and then casts to the declared schema. Any other type mismatch still fails the read, on purpose.
  • Count rows per day. The job logs the number of source rows for every requested day and warns on a day whose file has none. It costs almost nothing and would have caught both problems on the first run.
  • A test that fails on the old setting. It writes an unreadable file into a test folder and checks that the read fails instead of returning fewer rows.
df = (spark.read
      .option("ignoreCorruptFiles", "false")   # fail loudly; Spark retries transient errors
      .parquet(*paths_for(dates)))

per_day = df.groupBy("year", "month", "day").count().collect()
for d in dates:
    if rows_for(per_day, d) == 0:
        log.warning("no source rows for %s", d)

Takeaways

  • Any flag that turns errors into skips is a data-loss switch. ignoreCorruptFiles, ignoreMissingFiles, permissive parse modes. Know which of your reads have them on, and why.
  • Upserts hide missing input. With a MERGE, no rows means no change, which looks the same as "nothing new happened." Append-only loads at least show a gap.
  • Green is not the same as complete. A cheap per-partition row count in the logs is the difference between finding this in a day and finding it when someone asks why a chart has a dip.

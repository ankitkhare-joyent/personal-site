Why my Iceberg MERGE read 930 million rows to write 316 thousand

Ankit Khare · November 2026 · 3 min read

An hourly Iceberg load was taking 14 to 20 minutes to commit one file of about 316,000 rows. The MERGE looked like it only touched one day's partition. It was joining against the whole 930-million-row table.

The condition that looked fine

The target table is partitioned by year, month and day, and the batch carries the same columns. The merge condition matched them:

MERGE INTO lake.tags t
USING batch s
ON  t.resource_id = s.resource_id AND t.tag_key = s.tag_key
AND t.year = s.year AND t.month = s.month AND t.day = s.day
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *

Reading that, you would expect Spark to touch only the partitions in the batch. It doesn't have to. t.year = s.year is a join condition, not a filter. Spark can turn it into partition pruning only at runtime, using dynamic partition pruning, and only when the source side is small enough to broadcast. Most of our merges had small batches and were broadcast, so they pruned fine. The tags batch was not, so every hourly load planned a scan of the entire table.

The fix: give the planner literals

Every row in a batch comes from a known set of dates, because the batch is built from the list of dates being processed. So the job can put those dates on the target side as literals, in front of the existing condition:

def merge_condition(keys, dates):
    years  = sorted({d.year for d in dates})
    months = sorted({d.month for d in dates})
    days   = sorted({d.day for d in dates})
    prune = (f"t.year IN ({','.join(map(str, years))}) "
             f"AND t.month IN ({','.join(map(str, months))}) "
             f"AND t.day IN ({','.join(map(str, days))})")
    return prune + " AND " + " AND ".join(f"t.{k} = s.{k}" for k in keys)

Literals on the target are ordinary filters, so Spark pushes them into the Iceberg scan at planning time. The plan for the tags merge now shows filters=year = 2026, month = 10, day = 30.

The separate IN lists can over-include near a month boundary: dates of October 31 and November 1 give month IN (10, 11) AND day IN (1, 31), which also matches October 1. That is fine. The equality conditions still decide what matches, so a few extra partitions get read and nothing changes in the result. If no dates are passed, the condition is left exactly as it was.

Checking it

A change to a MERGE condition is the kind of thing you want to be boringly sure about. I ran the real merge code, schemas, conditions and update maps on a local Iceberg catalog, old condition against new:

  • all 16 datasets that use the merge: identical results, and only the new condition prunes at planning time;
  • the catch-up cases: missed hours earlier in the day, late rows from the previous day, month and year boundaries, and a month-long backfill;
  • a 43-million-row table with a batch too big to broadcast: 19.3 s to 2.1 s.

The other jobs' tables top out around 59 million rows with batches that do broadcast, so runtime pruning already worked for them.

Takeaways

  • Read the scan node, not the SQL. The physical plan or the Spark UI shows which filters reached the Iceberg scan. If your partition columns are not there, you are not pruning at planning time.
  • Runtime pruning is conditional. It depends on broadcast, which depends on batch size, which changes over time. A job that pruned fine last month can stop when one source grows.
  • Literals are a guarantee, but only if they are true. This works because every batch row provably comes from the listed dates. If you cannot prove that, a literal filter will silently skip rows you meant to update.

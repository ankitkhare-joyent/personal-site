185 Airflow DAG files to 97: consolidating a lakehouse's Spark jobs

Ankit Khare · November 2026 · 4 min read

Nobody asked for this one. Our lakehouse refresh took two to three hours, and every new table meant copying another Spark job and another Airflow DAG. Over five weeks I folded those per-table jobs into a few config-driven ones. A full refresh now takes minutes, and runs every hour.

How it got that way

The lakehouse at work loads infrastructure inventory into Apache Iceberg: EC2, VPC and IAM data from our cloud's admin APIs, plus monitoring, configuration management and data-center sources. It grew one table at a time, and the easy way to add a table was to copy the last one. So each output table had its own Spark application and its own DAG. VPC alone had 25 separate flatten applications. EC2 had 14.

Each of those applications started its own driver and executors, listed the same S3 prefixes, read the same source Parquet, and wrote one table. Most of the runtime was that overhead, repeated a few hundred times. The jobs also ran on fixed schedules that had nothing to do with when new data landed, so plenty of runs reprocessed data that had not changed.

The maintenance cost was just as bad. A fix to how we parse timestamps meant the same edit in 25 files, and reviewing it meant reading all 25.

The design

One application per source, with a registry of datasets. A dataset is just its source folder, a transform onto its output schema, and its merge keys:

DATASETS = {
    "subnets": Dataset(source="DescribeSubnets", schema=SUBNETS,
                       merge_keys=["subnet_id", "region"], sql=SUBNETS_SQL),
    "route_tables": Dataset(...),
    # 25 in all for VPC
}

def run(spark, datasets, max_parallel=4):
    def one(ds):
        s = spark.newSession()          # its own temp views and conf
        dates = dates_behind(s, ds)     # per table: a current table is skipped
        if not dates:
            return
        df = transform(s, ds, read_source(s, ds.source, dates))
        assert_schema(df, ds.schema)    # before anything is written
        merge(s, df, ds.merge_keys, dates)

    with ThreadPoolExecutor(max_parallel) as pool:
        results = {name: pool.submit(one, ds) for name, ds in datasets.items()}
    failed = [n for n, f in results.items() if f.exception()]
    if failed:
        raise RuntimeError(f"datasets failed: {failed}")

A few decisions did most of the work:

  • Dates are worked out per table. A table that is current is skipped, and one that is behind catches up in the same run. The job only lists and reads the source folders that some table actually needs.
  • Datasets run in parallel, each in its own Spark session. spark.newSession() gives each dataset its own temp views and conf, which is what makes concurrent Iceberg MERGEs from one application safe. spark.scheduler.mode=FAIR lets the concurrent stages share executors.
  • Schemas are checked before any write. The output schemas are imported unchanged from the old jobs and asserted during query analysis. Same tables, same partitioning, same merge keys, so nothing downstream had to change.
  • No driver actions on the hot path. No count(), collect() or isEmpty() before the write. The only pre-run work is listing S3 prefixes and analysing the queries.
  • One bad dataset does not stop the rest. Failures are collected, the others finish, and the job fails at the end with a summary.

Run when the data lands

The second half of the change was cadence. Ingestion writes new files on a known schedule, so each DAG now runs just after its source lands, instead of hourly or daily out of habit. Each run covers whatever range of dates is behind, rather than Airflow scheduling one run per missed interval. After a pause there is one catch-up run, not a queue of them.

With the jobs cheap enough, I added hour-level partitions for the EC2, VPC and IAM tables and moved them to hourly runs, with Iceberg maintenance (expiring snapshots, compacting small files) in its own daily job instead of inline.

Rolling it out

Four pull requests between September 10 and October 16: EC2 and VPC first, then hourly partitions and IAM, then the monitoring sources together with the cadence change, then configuration-management inventory, which also let me delete a set of aggregation DAGs. Doing it source by source meant each cut-over was small enough to check table by table.

What I'd tell someone about to do the same

  • Look at overhead before you add executors. Our jobs were not slow because the work was big. They were slow because the same start-up, listing and reading happened hundreds of times.
  • A shared job has a shared blast radius. A bug in one transform can now break 25 tables, so the schema check and per-dataset isolation are not optional extras.
  • Keep the outputs identical. Holding schemas, partitions and merge keys fixed turned a scary refactor into a mechanical one.
  • Log what the source does not have. A few fields the old jobs populated were not in the flattened source at all. They are listed in the code and logged every run, instead of quietly turning into nulls.

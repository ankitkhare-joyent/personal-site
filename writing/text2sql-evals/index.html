How I evaluate a Text2SQL agent

Ankit Khare · November 2026 · 5 min read

"It answered my three test questions" is not a measurement. Here is the small, boring setup I use to know whether a Text2SQL agent is actually right, and what it taught me about where these systems fail.

I build Text2SQL systems over an Apache Iceberg lakehouse: one at work, and an open lab, semantic-txt-2-sql, where the same EC2 fleet question gets answered three ways. The agent can go through a semantic layer (Cube), write raw SQL against Trino, or do a hybrid of both. Everything below comes from that lab, so you can rerun it.

1. Write the truth by hand, and put a trap in it

The eval set is a YAML file of questions, each with a hand-written truth SQL. The interesting part is the trap each question sets, because that is where agents go wrong:

  • Grain. The fleet table is a snapshot every two hours. "GPU hours in August" has to multiply each snapshot row by 2. "How many are running now" has to use only the latest snapshot.
  • Semi-additive measures. "Average concurrent instances in May" divides by the number of distinct snapshots, not by rows.
  • Business rules. Cost needs a price book and a 35% spot discount that live in the semantic layer, not in the data.
  • Value grounding. Filters like a team or a region have to match the real spelling in the data.
  • Security. One question asks, as a restricted persona, for rows that persona must never see. The right answer is "denied".

Eleven questions is a teaching set, not a benchmark. That is fine. Each one exists because it catches a specific mistake.

2. Grade the answer, not the SQL

Two correct queries rarely look alike, so comparing SQL strings is useless. The runner computes the truth on Trino as an admin, asks the agent, and grades the value it submits: within 0.5% relative tolerance, or an absolute tolerance for small numbers. Every step the agent took goes into a .jsonl trace, so when something fails I read the trace before blaming the model. Sometimes the truth SQL is the thing that is wrong.

3. Keep a hold-out set you never tune on

This is the lesson I learned the hard way. Once you start fixing prompts, table notes and column comments to make failing questions pass, your eval set stops measuring the agent. It starts measuring how well you fit the eval set. On the system I run at work, accuracy on the questions I had tuned against was several points higher than on a held-out set of questions over tables the prompts never mentioned.

So now every eval set has a hold-out slice with two rules: no question in it is ever used to change a prompt, and no ID or value from it appears in the notes. I report both numbers, side by side. The hold-out number is the one I believe.

4. What the lab showed

One run, Claude Opus 5.5, medium effort, all eleven questions in each mode:

Semantic layer11/117.71.3341
Raw SQL10/1112.52.5858
Hybrid11/116.01.4382

Three things stood out.

The model is good at SQL now. With a flat, documented fact table, raw SQL handled every grain trap. Most of the credit goes to the lakehouse doing its part: column docs, one clean fact table. On a raw fifteen-table normalised schema I would expect it to drop sharply.

Raw SQL cannot know what is not in the data. The one miss was the cost question, because the price book lives only in the semantic layer. And the model refused rather than inventing prices, then reported what it could measure. That is the failure you want. It came from one line in the system prompt telling the agent to say when the data cannot answer. Remove that line and you get a confident, made-up number.

The semantic path is cheaper. Half the tool calls and less than half the output tokens, because the model picks measures instead of writing, checking and fixing SQL. Hybrid behaved like semantic mode on every question while keeping SQL available for anything outside the model, which is why I would ship hybrid.

5. Guardrails belong in the eval

The security question passed in every mode: Cube's access policy blocked it in semantic mode, Trino's row filter in SQL mode. I treat that as a test, not a feature. In production I also run every generated query through a sqlglot guard before it reaches the engine, and protect sensitive columns with policies that fail closed. If a guardrail is not in the eval set, you find out it broke from a user.

6. Caveats, before anyone quotes the numbers

  • One trial is not enough. LLM output varies between runs. Run each question several times and look at the spread, not just the mean.
  • Grow the set from real failures. Every question a user asks that the agent got wrong becomes a new case. A good eval set is a log of your mistakes.
  • Watch the cost columns too. Accuracy is not the only metric. Latency and tokens decide whether people keep using it.
If you only take one thing: keep a hold-out set, report it next to your tuned number, and trust the lower one.
